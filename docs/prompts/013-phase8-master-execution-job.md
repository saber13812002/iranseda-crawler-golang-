# مرحله B5 — Canonical Dedup & Schedule Versioning

## هدف

ایجاد هویت پایدار برای برنامه‌ها و اپیزودها و ثبت تغییرات زمان‌بندی.

### B5.1 هویت برنامه

شناسه اصلی برنامه باید شناسه پایدار `m` باشد.

برای مثال:

- برنامه روایت کتاب
- شناسه m=049113
- کانال 14

تغییر ساعت پخش نباید موجب ساخته شدن یک برنامه جدید شود.

### B5.2 هویت اپیزود

کلید یکتای اپیزود باید بر مبنای:

`channel_id + episode_id (e)`

باشد.

فرمت‌های مختلف URL، پارامتر VALID، ترتیب پارامترها، آدرس نسبی و مطلق نباید اپیزود تکراری بسازند.

تمام مسیرهای ورود اطلاعات باید از منطق Dedup یکسان استفاده کنند:

- Go Scanner
- Python Discovery
- Dashboard Seed
- Backfill
- Manual Add

### B5.3 نسخه‌بندی زمان‌بندی

یک ساختار تاریخی برای Schedule ایجاد کن.

هر نسخه باید حداقل شامل:

- program_id
- m
- channel_id
- start_time
- duration
- weekdays
- valid_from
- valid_until
- detected_at
- source
- confidence
- schedule_version

باشد.

زمان‌بندی جدید نباید اطلاعات قبلی را بازنویسی و حذف کند.

تغییر ساعت باید به‌عنوان نسخه جدید Schedule ثبت شود.

### B5.4 تشخیص تغییر زمان پخش

برنامه باید از نظر موارد زیر بررسی شود:

- ساعت شروع
- روزهای پخش
- مدت برنامه
- تعداد دفعات پخش
- فاصله بین اپیزودها

اگر تغییر زمان‌بندی مشاهده شد، ابتدا با شواهد EPG و آرشیو بررسی شود.

تغییر زمان به‌تنهایی دلیل تغییر هویت برنامه نیست.

### تست‌های اجباری

1. ورود دوباره یک URL با شکل متفاوت.
2. ورود دوباره همان اپیزود با پارامترهای جابه‌جا شده.
3. تغییر ساعت یک برنامه.
4. تغییر روزهای پخش.
5. بازگشت به زمان‌بندی قبلی.
6. وجود دو اپیزود متفاوت از یک برنامه در یک روز.
7. جلوگیری از ثبت دوباره اپیزود پس از اجرای مجدد Scanner.

### معیار پذیرش

- صفر Duplicate در کلیدهای Canonical.
- عدم از بین رفتن Schedule History.
- یکسان بودن منطق Go و Python.
- تست Regression موفق.

# مرحله B7 — Program Backfill Engine

## هدف

بازیابی اپیزودهای قدیمی که در صفحات فعلی فهرست برنامه نمایش داده نمی‌شوند.

در حال حاضر سیستم عمدتا‌ به تعداد محدودی از اپیزودهای جدید دسترسی دارد. باید امکان عقب رفتن در آرشیو ایجاد شود.

### B7.1 روش پیمایش

از منابع موجود استفاده کن:

- epgList
- epgarchivePart
- radiolist
- EPG Archive
- لینک‌های دانلود واقعی

با Pagination پنج‌تایی یا مقدار قابل تنظیم در Settings به عقب برو.

### B7.2 تنظیمات قابل کنترل

در Settings امکان تعریف موارد زیر باشد:

- تعداد اپیزود در هر صفحه
- حداکثر اپیزود Backfill روزانه
- حداکثر تعداد صفحات پیمایش
- حداکثر تعداد دانلود هم‌زمان
- حداکثر تعداد Jobهای ASR
- حداقل Confidence محتوایی
- حد توقف Backfill
- تعداد خطاهای مجاز
- امکان Pause و Resume
- اولویت برنامه‌ها

مقادیر اولیه پیشنهادی:

`BACKFILL_PAGE_SIZE=5`

سایر مقادیر بر اساس ظرفیت واقعی سرور و با پیش‌فرض محافظه‌کارانه تعیین شوند.

### B7.3 تشخیص استمرار برنامه

هر اپیزود جدید باید با برنامه هدف تطبیق داده شود.

از موارد زیر استفاده کن:

- شناسه برنامه m
- عنوان
- توضیحات
- مدت
- زمان پخش
- روزهای پخش
- متن تولیدشده
- نمونه‌های قبلی برنامه

از LLM برای ارزیابی محتوایی استفاده کن، اما تصمیم فقط متکی به LLM نباشد.

### B7.4 قانون توقف

اگر برنامه در گذشته تغییر کرده باشد، Backfill نباید بی‌نهایت ادامه پیدا کند.

وضعیت هر اپیزود یکی از این موارد باشد:

- MATCH_CONFIRMED
- MATCH_PROBABLE
- REVIEW_REQUIRED
- PROGRAM_CHANGED
- DUPLICATE
- NO_AUDIO
- DOWNLOAD_FAILED

در صورت مشاهده تغییر قطعی برنامه یا Schedule، توقف خودکار همان شاخه Backfill انجام شود.

برای موارد نامطمئن، تأیید انسانی درخواست شود.

### B7.5 حفظ داده

هیچ فایل صوتی اصلی حذف نشود.

هیچ اپیزود قبلی بازنویسی نشود.

خروجی ASR جدید با شناسه مدل، Prompt و تاریخ پردازش جداگانه ثبت شود.

### تست‌های اجباری

1. Backfill پنج اپیزود یک برنامه.
2. اجرای مجدد همان Backfill.
3. توقف و Resume.
4. کشف اپیزود تکراری.
5. کشف تغییر برنامه در گذشته.
6. خطای دانلود.
7. نبود صوت.
8. عبور از مرز تغییر Schedule.

## 3. بازگرداندن چرخه خودکار Commit و Reporting

هدف این است که پروژه دوباره بدون دخالت روزانه مدیر، وضعیت خود را ثبت و منتشر کند.

### 3.1 Commit Automation

چرخه مورد انتظار:

1. اجرای Pipeline
2. تولید SRT و TXT
3. تولید سایت
4. تولید آمار
5. تولید گزارش عملیاتی

8. تأیید Remote
9. بررسی محتوای سایت عمومی

هدف زمانی:

- Pipeline: هر ۳۰ دقیقه
- Site Refresh: هر ۳۰ دقیقه یا طبق معماری فعلی

- Reporter: طبق برنامه مستندشده و قابل تنظیم

توجه:

اگر هیچ فایل جدیدی وجود ندارد، Commit خالی تولید نکن.

در این حالت باید اجرای موفق بدون تغییر، در گزارش عملیاتی و متریک‌ها ثبت شود.

### 3.2 جلوگیری از Commit تکراری

- تنها فایل‌های خروجی مورد تأیید Stage شوند.
- فایل‌های Credential، DB Dump و Audio وارد Git نشوند.
- Commitهای هم‌زمان با Lock مدیریت شوند.
- Push ناموفق باعث از دست رفتن Commit محلی نشود.
- Retry محدود و قابل ردیابی باشد.

## 8. سیستم تشخیص انحراف از وضعیت سالم

یک بخش با عنوان:

`Operational Drift Detection`

ایجاد کن.

سیستم باید اختلاف بین وضعیت فعلی و Baseline را به‌صورت خودکار شناسایی کند.

مثال:

- قبلا‌ هر ساعت Commit داشتیم، اکنون ۸ ساعت Commit نداریم.
- قبلا‌ Reporter اجرا می‌شد، اکنون متوقف شده است.
- قبلا‌ سایت هر نیم ساعت تغییر می‌کرد، اکنون دو روز ثابت مانده است.
- تعداد SRTهای امروز صفر است.
- Queue پر است ولی Worker پیشرفتی ندارد.
- LLM از دسترس خارج شده است.
- برنامه‌های فعال هستند ولی هیچ خروجی تولید نمی‌کنند.

هر انحراف باید دارای:

- Severity
- First Detected
- Last Observed
- Affected Component
- Baseline Value
- Current Value
- Probable Root Cause
- Evidence
- Suggested Remediation

باشد.

### سیاست تصمیم‌گیری

- انحراف کم‌خطر: خودکار اصلاح و گزارش شود.
- اختلال قابل بازیابی: تلاش محدود برای بازیابی و ثبت نتیجه.
- اختلال حیاتی: Feature Development متوقف شود.
- تغییر مخرب یا نامطمئن: از مدیر تصمیم گرفته شود.
