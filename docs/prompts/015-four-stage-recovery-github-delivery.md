## دستور مأموریت

شما ایجنت اجرایی مستقر روی زیرساخت پروژه ایران‌صدا هستید.

هدف: در چهار مرحله، وضعیت پروژه را بررسی، مشکلات عملیاتی را اصلاح، تولید زیرنویس و گزارش‌سازی را اعتبارسنجی و تمام نتایج را به GitHub منتقل کنید.

**مقصد اصلی تحویل:**
`https://github.com/saber13812002/iranseda-crawler-golang-`

گزارش‌ها باید در Repository ثبت شوند، نه صرفا‌ در ترمینال یا پوشه موقت سرور.

## قوانین غیرقابل مذاکره

1. هیچ فایل یا تغییر قبلی حذف نشود.
2. قبل از هر مرحله `git status` و diff بررسی شود.
3. از `git reset --hard`، `git clean -fd` و Force Push استفاده نشود.
4. فایل‌های `.env`، رمزها، توکن‌ها، دیتابیس و فایل‌های صوتی Commit نشوند.
5. هیچ موفقیتی بدون تست واقعی گزارش نشود.
6. هر مرحله Commit مستقل داشته باشد.
7. بعد از هر مرحله Push به GitHub انجام و SHA تأیید شود.
8. اگر یک مرحله شکست خورد، شواهد شکست ذخیره شود و مرحله بعدی خرابی را پنهان نکند.
9. از اجرای موازی و تداخل با Workerهای فعال خودداری شود.
10. هیچ عملیات مخربی روی دیتابیس یا صف تولید انجام نشود.

# STAGE 1 — PREFLIGHT, PRESERVATION & CHECKPOINT

### هدف
حفظ تمام کارهای قبلی و شناخت وضعیت واقعی پروژه.

### اقدامات

1. روی سرور ۵۳ Repository اصلی را پیدا کنید.
2. Branch، Remote، آخرین Commit و وضعیت Working Tree را استخراج کنید.
3. تمام فایل‌های تغییرکرده و Untracked را فهرست کنید.
4. فایل‌های 013 و 014 را بررسی کنید.
5. تغییرات قبلی را با آخرین Commit مقایسه کنید.
6. وجود تغییرات حساس یا اطلاعات محرمانه را بررسی کنید.
7. اتصال GitHub را آزمایش کنید.
8. وضعیت GitLab داخلی را نیز بررسی کنید؛ ولی مقصد اصلی این مأموریت GitHub است.
9. شاخه عملیاتی و شاخه‌ای که GitHub Pages از آن منتشر می‌شود را جداگانه شناسایی کنید.

### Commit

پس از بررسی و حفاظت از تغییرات:

`chore(checkpoint): preserve pre-phase8 work`

فقط فایل‌های بررسی‌شده و مجاز را Stage کنید.

### تست پذیرش

- فایل‌های قبلی حفظ شده باشند.
- Commit ایجاد شده باشد.
- Push موفق باشد.
- SHA محلی و Remote یکسان باشند.
- Working Tree وضعیت مشخص و مستند داشته باشد.

### گزارش

`reports/phase8/STAGE_1_PREFLIGHT.md`

# STAGE 2 — OPERATIONAL RECOVERY & REPORTER

### هدف
اطمینان از اینکه Pipeline و سرویس گزارش‌ساز واقعا‌ اجرا می‌شوند.

### اقدامات

روی سرور ۵۳:

1. Cron و زمان‌بندی تمام Jobها را بررسی کنید.
2. زمان آخرین اجرای واقعی Pipeline را استخراج کنید.
3. زمان آخرین اجرای `refresh_site.sh` را بررسی کنید.
4. وضعیت executable بودن اسکریپت‌ها را بررسی کنید.
5. تاریخ آخرین Commit خودکار را با زمان اجرا مقایسه کنید.
6. وضعیت systemd و Workerها را بررسی کنید.
7. سرویس Reporter و Job گزارش‌سازی را پیدا کنید.
8. بررسی کنید چرا گزارش‌ها تولید نشده‌اند.
9. آخرین اجرای موفق و آخرین اجرای ناموفق را با لاگ واقعی شناسایی کنید.

### اصلاح

هر مشکل اثبات‌شده را اصلاح کنید.

به‌خصوص:
- Cron باید واقعا‌ اجرا شود.
- Refresh باید خروجی جدید را تشخیص دهد.
- Reporter باید مستقل از موفقیت یا شکست Pipeline گزارش تولید کند.
- Commit خودکار نباید Push ناموفق را پنهان کند.

یک اجرای کنترل‌شده واقعی انجام دهید.

### تست پذیرش

- یک اجرای واقعی Pipeline ثبت شود.
- یک اجرای واقعی Reporter ثبت شود.
- گزارش حتی در صورت صفر بودن خروجی ساخته شود.
- وضعیت Push بررسی شود.
- هیچ اجرای هم‌زمان متداخل وجود نداشته باشد.

### Commit

`fix(ops): restore pipeline and reporter execution`

### گزارش

`reports/phase8/STAGE_2_OPERATIONAL_RECOVERY.md`

# STAGE 3 — SRT CONTINUITY, QUEUE & GRAFANA

### هدف
بازگرداندن و اثبات تولید مستمر زیرنویس.

### اقدامات روی سرور ۵۳

موارد زیر را از دیتابیس واقعی استخراج کنید:

- تعداد SRT امروز به وقت تهران
- تعداد SRT دیروز
- تعداد SRT در ۷ روز گذشته
- تعداد SRT در ۳۰ روز گذشته
- آخرین زمان تولید SRT
- تعداد فایل‌های Pending Download
- تعداد Pending Transcribe
- تعداد Transcribing
- تعداد Failed
- تعداد برنامه‌های متمایزی که در هر روز SRT جدید داشته‌اند

توجه: تعداد فایل زیرنویس و تعداد برنامه متمایز را جداگانه محاسبه کنید.

### بررسی ظرفیت

1. وضعیت Workerهای Whisper و ASR روشن را بررسی کنید.
2. ظرفیت آزاد GPU و محدودیت هم‌زمانی را بررسی کنید.
3. صف‌های دانلود و پردازش را بررسی کنید.
4. گلوگاه واقعی را پیدا کنید.
5. Backfill را فقط با کنترل ظرفیت و Dedup اجرا کنید.
6. برنامه‌های جدید را فقط در صورت نبودن نسخه قبلی اضافه کنید.
7. تغییر ساعت پخش یک برنامه نباید باعث تکرار اپیزود شود.

هدف عملیاتی اولیه: روزانه ۵ تا ۱۰ برنامه متمایز با زیرنویس جدید، در صورت وجود فایل صوتی قابل دریافت.

### Grafana روی سرور ۵۲

داشبورد موجود را پیدا کنید:

`iranseda-pipeline`

پنل‌های زیر را بررسی و تکمیل کنید:

- تعداد اجراهای ۳۰ دقیقه‌ای
- تعداد اجراهای بدون کار جدید
- تعداد اجراهای ناموفق
- SRT روزانه
- SRT هفتگی و ماهانه
- آخرین SRT تولیدشده
- صف دانلود
- صف زیرنویس
- خطاهای دائمی
- وضعیت Reporter
- وضعیت انتشار GitHub Pages
- Operational Health Score

پنل‌های قبلی را حذف نکنید.

اگر Grafana از File Provisioning استفاده می‌کند، ابتدا نسخه فعلی را Backup کنید، JSON را اعتبارسنجی کنید و سپس نسخه جدید را Deploy کنید.

تمام Queryهای جدید را در Prometheus با داده واقعی آزمایش کنید.

### تست پذیرش

- Pipeline واقعی اجرا شود.
- وضعیت صف‌ها قابل مشاهده باشد.
- SRT واقعی تولید شود یا علت دقیق عدم تولید ثبت شود.
- داده‌های Grafana با دیتابیس تطبیق داشته باشند.
- اجرای بدون کار به‌عنوان یک وضعیت مستقل ثبت شود.

### Commit

`feat(monitoring): restore SRT continuity metrics and Grafana reporting`

### گزارش

`reports/phase8/STAGE_3_SRT_AND_MONITORING.md`

# STAGE 4 — GITHUB PUBLICATION & FINAL ACCEPTANCE

### هدف
تمام نتایج چهار مرحله روی GitHub قابل مشاهده باشند.

### اقدامات

1. تمام گزارش‌های مراحل قبلی را بازبینی کنید.
2. وضعیت نهایی هر سرویس را ثبت کنید.
3. فایل‌های زیر را ایجاد یا به‌روزرسانی کنید:

- `docs/PROJECT_STATE.md`
- `docs/OPERATIONS_BASELINE.md`
- `docs/OPERATIONAL_SLO.md`

4. گزارش جامع نهایی را ایجاد کنید:

`reports/phase8/FOUR_STAGE_FINAL_REPORT.md`

5. تمام تغییرات را Commit کنید.
6. Push را انجام دهید.
7. SHA محلی و Remote را تطبیق دهید.
8. فایل‌های گزارش را از GitHub Raw دریافت و وجود محتوای واقعی آن‌ها را تأیید کنید.
9. اگر GitHub Pages در دسترس است، Hash محتوای عمومی را با Commit منتشرشده مقایسه کنید.
10. اگر Pages هنوز روی Branch اشتباه است، آن را صریحا‌ BLOCKED گزارش کنید؛ HTTP 200 را معادل انتشار صحیح ندانید.

### Commit

`docs(phase8): publish four-stage operational recovery report`

### تست پذیرش

- چهار گزارش مرحله‌ای در GitHub موجود باشند.
- گزارش نهایی در GitHub موجود باشد.
- تمام Commitها SHA معتبر داشته باشند.
- لینک گزارش‌ها قابل باز شدن باشند.
- نتایج واقعی و موارد ناقص از هم تفکیک شده باشند.
