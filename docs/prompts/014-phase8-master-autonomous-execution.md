# بخش صفر — قوانین غیرقابل مذاکره

## قانون ۱: ابتدا حفاظت از وضعیت فعلی

قبل از هر تغییری:

- Repositoryها را شناسایی کن.

- فایل‌های جدید و حذف‌شده را بررسی کن.
- آخرین وضعیت Remoteها را دریافت کن.
- تغییرات قبلی را بدون بررسی حذف یا بازنویسی نکن.

### Commit اولیه اجباری

در ابتدای مأموریت، پیش از تغییر کد:

1. تمام تغییرات موجود را بررسی کن.
2. تغییرات متعلق به کارهای قبلی را از فایل‌های موقت، Credential و خروجی‌های غیرقابل انتشار تفکیک کن.
3. تست‌های مناسب را اجرا کن.
4. تغییرات سالم و قابل شناسایی را در یک Commit مستقل با عنوان مناسب مانند زیر ثبت کن:

`chore(checkpoint): preserve pre-phase8 work`

5. آن را روی Remoteهای معتبر Push کن.
6. تطبیق SHA را بررسی کن.

اگر تغییرات موجود قابل تفکیک نیستند یا احتمال ورود اطلاعات محرمانه وجود دارد، هیچ Commit کورکورانه‌ای انجام نده. از وضعیت نسخه پشتیبان و Patch قابل بازیابی تهیه کن و موضوع را گزارش بده.

هرگز از `git add -A` بدون بررسی استفاده نکن.

## قانون ۲: دو مقصد Git اجباری

تمام تغییرات مربوط به پروژه باید در مقصدهای مربوطه منتشر شوند:

### کشف اتصال GitLab

گزارش شده که IP سرور GitLab داخلی تغییر کرده است.

بنابراین:

- IP قدیمی را مبنای اتصال قرار نده.
- ابتدا DNS دامنه `git.ai.ismc.ir` را بررسی کن.
- از `getent hosts`، `getent ahosts`، `dig` یا `nslookup` استفاده کن.
- IPهای پاسخ DNS را ثبت کن.
- اتصال SSH یا HTTPS را مطابق Remote موجود آزمایش کن.
- TLS و Host Key را بررسی کن.
- از Credentialهای موجود و مجاز استفاده کن.
- در صورت نیاز از SSH غیرتعاملی استفاده کن.
- Remote واقعی GitLab را از تنظیمات Repository و مستندات پیدا کن.
- نام Repository و مسیر پروژه را حدس نزن.
- از چاپ Token، Password، Private Key و اطلاعات محرمانه خودداری کن.

نمونه بررسی:

`git remote -v`

`git ls-remote origin`

`ssh -T git@git.ai.ismc.ir`

در صورت استفاده از SSH، پورت و Host Key را بر اساس تنظیمات واقعی سرویس بررسی کن.

اگر DNS درست Resolve شد ولی اتصال برقرار نشد، علت را تفکیک کن: DNS، Routing، Port، SSH، TLS، Authentication یا مجوز Repository.

هیچ‌گاه برای حل مشکل، Host Key Checking را غیرفعال نکن.

### سیاست انتشار دوگانه

برای هر Repository مرتبط:

- GitHub و GitLab را جداگانه بررسی کن.
- Branch متناظر را شناسایی کن.
- Commitها را با یکدیگر مقایسه کن.
- Push را بدون Force انجام بده.
- Remote HEAD را بعد از Push بررسی کن.
- در صورت Divergence، قبل از Rebase یا Merge نسخه پشتیبان بساز و تاریخچه را تحلیل کن.
- از Push کردن کورکورانه یک Branch به Branch دیگر خودداری کن.

اگر یک مقصد موفق و مقصد دیگر ناموفق بود، وضعیت آن مرحله PARTIAL است؛ نه PASS.

از `git push --force` و `git push --mirror` استفاده نکن.

آمار بر اساس تعداد واقعی رکوردهای دارای وضعیت subtitled و فایل خروجی معتبر باشد.

### 4.2 بررسی صف‌ها

- pending_download

- failed_permanent

روند پیشرفت هر صف را در چند بازه زمانی بررسی کن.

صرفا‌ بزرگ بودن Queue به معنی سلامت یا خرابی نیست.

### 4.3 ظرفیت پردازش

بررسی کن:

- GPUهای آزاد
- GPUهای مشغول
- CPU و RAM
- Workerهای فعال
- محدودیت‌های Docker
- زمان پردازش هر فایل
- امکان موازی‌سازی امن
- محدودیت APIهای ASR

در صورت امکان از ظرفیت آزاد استفاده کن؛ بدون آنکه Workerهای موجود دچار تداخل شوند.

### 4.4 جلوگیری از روزهای بدون خروجی

هدف اولیه:

روزانه حداقل ۵ تا ۱۰ برنامه متمایز دارای زیرنویس جدید داشته باشیم.

این هدف باید با محتوای واقعا‌ قابل دریافت و قابل پردازش سنجیده شود.

اگر منبع و کار واجد شرایط وجود دارد ولی خروجی صفر است، علت باید شناسایی شود.

اگر Queue خالی است یا منبع جدید وجود ندارد، صفر خروجی را به‌عنوان خرابی ثبت نکن؛ علت را مشخص کن.

### 4.5 Backfill

Backfill را بر اساس اولویت، ظرفیت و سقف قابل تنظیم انجام بده.

- از پردازش تکراری جلوگیری کن.
- ابتدا یک برنامه و تعداد محدود اپیزود را Canary کن.
- خروجی واقعی را تأیید کن.
- سپس تدریجی گسترش بده.
- اطلاعات اپیزود و فایل اصلی حفظ شود.

برای Backfill نامحدود یا حذف فایل‌های اصلی اقدام نکن.

# سه نکته مهم درباره نحوه اجرای این پرامپت
